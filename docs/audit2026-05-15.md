# Comprehensive Codebase Audit — LicenseManagement.EndUser.Wpf

**Audit Date:** 2026-05-15
**Branch:** master
**Target:** Full repository (treated as fresh code review)
**Auditor:** senior-dotnet (multi-lens: clean-code, design-patterns, security-review, external-integrations-review, WPF/XAML best-practices)
**Severity Scale:** Critical / High / Medium / Low / Info

---

## 1. Architecture & Design Overview

**Project type:** .NET Framework 4.8.1 WPF Class Library distributed as a NuGet package (`LicenseManagement.EndUser.Wpf`). Provides MVVM-style views (`MainWindow`, `LicenseControl`, `RegisterLicenseView`, `UnregisterView`, `ErrorView`), view models, value converters, and a validation rule wrapping the underlying `LicenseManagement.EndUser` SDK.

### Strengths
- Clear separation between Views / ViewModels / Converters / Commands / Rules.
- Uses `INotifyPropertyChanged` via a `BaseViewModel`.
- `LicenseControl` as embeddable `UserControl` alongside `MainWindow` is a clean affordance.
- Sample app under `samples/WpfSampleApp` demonstrates an idiomatic `LicenseService` wrapper.

### Structural Concerns
- **MVVM is mixed with code-behind:** `MainWindow.xaml.cs` and `LicenseControl.xaml.cs` carry configuration-reading logic, image initialization, and dependency-property registration tied to `ConfigurationManager`. Configuration parsing should live in a settings/service class, not in a control.
- **Massive XAML resource duplication:** identical 60-line `<Window.Resources>` blocks (Thicknesses, Styles, Templates) appear in `MainWindow.xaml`, `LicenseControl.xaml`, `ErrorView.xaml`, `RegisterLicenseView.xaml`, `UnregisterView.xaml`. The `AppResources.xaml` ResourceDictionary already defines all of these, but each view re-defines them locally — defeating the entire purpose of the shared resource dictionary.
- **Two orphan files (`Window1.xaml`, `Window1.xaml.cs`)** are scaffolding leftovers. They are referenced in the `.csproj` and ship with the assembly but serve no purpose.
- **`ErrorViewModel` is empty** — declared `internal class ErrorViewModel : BaseViewModel { }` but `ErrorView` binds directly to `Exception`, never to this view model. Dead code.
- **`BooleanToVisibilityConverter` is unused** in any XAML in the project (verified by grep over `.xaml` files).
- **Configuration coupling:** `MainWindow.LicenseControl.Meta` reads from `ConfigurationManager.AppSettings` at type-initializer time — making the library impossible to use without an `app.config` block and impossible to unit-test.
- **No tests** in the repository at all.
- **Public API surface is too broad:** internal data-shape view models (`LicenseViewModel`, `BaseViewModel`, `ProductViewModel`) are `public`, while `UnregisterViewModel` is public but `RegisterLicenseViewModel` is `internal` — inconsistent visibility.

## 2. Per-Lens Findings

### 2.1 Clean-Code Audit

#### Critical
- **`Views/MainWindow.xaml.cs:70`** — `foreach (var item in ps.AllKeys)` runs **without a null check on `ps`**. If `Products` config section is missing, the `LicenseControl` path null-checks (`if (ps != null)` at `LicenseControl.xaml.cs:74`), but `MainWindow.Meta` does not — guaranteed `NullReferenceException` for any consumer that has app settings but no `Products` section. **Fix:** mirror the null guard from `LicenseControl.xaml.cs:74`.
- **`Views/LicenseControl.xaml.cs:33`** — `public static DependencyProperty LicenseProperty { get; }` is declared **without a setter and never assigned in the field initializer**, but is then assigned inside a static constructor that runs *after* `Meta` (an auto-property used inside the same static constructor). Because `LicenseProperty` is `{ get; }` (read-only auto-property compiles to a `readonly` field), the static constructor assignment works — but the pattern is fragile and identical bug exists in `MainWindow.xaml.cs:27`. The risk: `Meta` accesses `ConfigurationManager` at type-load time, which can throw `ConfigurationErrorsException` and leave the type permanently broken (`TypeInitializationException` on every subsequent reference). **Fix:** wrap `Meta` in try/catch returning `null` on failure; defer config reads to a lazy initializer.
- **`Commands/RelayCommand.cs:11`** — Constructor accepts `Predicate<object> canExecute` with no null guard. Every consumer that passes `null` (look at `LicenseViewModel.cs:265` — they always pass `(s) => true`, but the contract permits null) gets a `NullReferenceException` on the first `CanExecute` query. **Fix:** allow null and short-circuit to `true`, or guard with `ArgumentNullException`.
- **`Commands/RelayCommand.cs:17`** — `event EventHandler CanExecuteChanged;` is declared but never raised. WPF's `CommandManager` won't requery automatically unless this is wired to `CommandManager.RequerySuggested`. Result: buttons stay in a stale enabled/disabled state until a focus change. **Fix:** `public event EventHandler CanExecuteChanged { add { CommandManager.RequerySuggested += value; } remove { CommandManager.RequerySuggested -= value; } }`.

#### High
- **`ViewModels/LicenseViewModel.cs:265–267`** — Three `ICommand` properties are written as `=> new RelayCommand(...)` getters. **Every WPF binding evaluation allocates a fresh `RelayCommand`**, defeating any `CanExecute` caching and creating GC pressure. **Fix:** cache as private readonly fields initialized once.
- **`ViewModels/LicenseViewModel.cs:284`** — `catch (Exception)` swallows the exception object. The next line calls `context.Exception` (assuming the SDK populated it). If the SDK ever throws an exception that doesn't update `context.Exception`, the user sees `null`. **Fix:** `catch (Exception e) { ... ShowErrorView(obj as MainWindow, context.Exception ?? e); }`.
- **`ViewModels/RegisterLicenseViewModel.cs:50`** — `view.receiptCode.Text` reaches into the View's named control. Tight coupling that breaks MVVM. **Fix:** bind `ReceiptCode` two-way and check the view model property instead.
- **`ViewModels/RegisterLicenseViewModel.cs:89–96`** — `ChangeDefaultTrail` and `ComputerUnregistered` are empty no-op methods passed as callbacks. Either implement or remove from the handler call.
- **`ViewModels/ProductViewModel.cs:33–55`** — `Id` and `Name` setters compare `_id != value` then assign **but never call `OnPropertyChanged()`**. Binding listeners on these properties will never fire — silent broken-binding bug.
- **`ViewModels/LicenseViewModel.cs:186–196`** — `Product` setter has asymmetric logic: first-set path doesn't compare, second-set compares `Id`. If the same product instance is reassigned with mutated `Id`, the setter behaves inconsistently. **Fix:** simplify to a single `if (_product != value) { _product = value; OnPropertyChanged(); }`.
- **`Converters/ValueConverters/LicenseStatusConverter.cs:39, 101, 132`** — All status switches `default: return "Unknown"` (or empty brush). If the SDK adds a new `LicenseStatusTitles` enum value, the UI silently shows "Unknown" instead of failing visibly. **Fix:** at minimum, log a diagnostic; consider `throw new ArgumentOutOfRangeException` in debug builds.
- **`Converters/ValueConverters/LicenseStatusConverter.cs:23`** — Unchecked cast `(LicenseStatusTitles)value` — if `value` is `DependencyProperty.UnsetValue` or `null` (which WPF can pass during teardown), this throws `InvalidCastException` inside a converter, polluting the binding error log. **Fix:** `if (value is LicenseStatusTitles st) { ... } else return Visibility.Collapsed;` in every converter in the file.
- **`Converters/ValueConverters/UtcToLocalTimeConverter.cs:11`** — Caller is presumably passing a `DateTime?`. After `is DateTime date` pattern unwraps it, `date.Kind` is `Unspecified` (because `DateTime?` from XML serialization typically doesn't preserve kind). `ToLocalTime()` on an `Unspecified` kind treats it as local already and may double-convert. **Fix:** `DateTime.SpecifyKind(date, DateTimeKind.Utc).ToLocalTime()` before formatting.
- **`Views/LicenseControl.xaml.cs:44–53`** — Both `LicenseChanged` (static callback) and `OnLicenseChanged` (virtual instance method) exist but `OnLicenseChanged` is dead: the static callback never invokes it. Same dead code in `Views/MainWindow.xaml.cs:37–48`.
- **`Views/MainWindow.xaml.cs:94`** — Misspelled handler `OnProductsSlectionChanged` (should be `Selection`). Referenced from `MainWindow.xaml:193`. Renaming is a breaking change for anyone subclassing — but the typo is documented evidence of insufficient review.
- **`Window1.xaml` / `Window1.xaml.cs`** — Scaffolding leftover. Delete both files and the `.csproj` references at lines 89–91 and 116–119.

#### Medium
- **`ViewModels/BaseViewModel.cs:44–57`** — `ShowErrorView` couples the *base view model* to a concrete `View` (`ErrorView`). MVVM inversion violation. Move dialog presentation to a `IDialogService`.
- **`ViewModels/ErrorViewModel.cs`** — Empty class, includes unused `using System.Linq;` etc. Delete or implement.
- **`ViewModels/LicenseViewModel.cs:11–17`** — Unused `using` directives: `System.Runtime.CompilerServices`, `System.Runtime.InteropServices`, `System.Security`, `System.Security.Cryptography`, `System.Windows.Documents`, `System.Xml.Serialization` (the `[XmlType]` is used, keep that), `System.Collections.Generic`.
- **`ViewModels/RegisterLicenseViewModel.cs:4–11`** — Unused: `System.Collections.Generic`, `System.Collections.ObjectModel`, `System.Linq`, `System.Security`, `System.Text`, `System.Threading.Tasks`.
- **`ViewModels/UnregisterViewModel.cs:3–7`** — Unused: `System`, `System.Collections.ObjectModel`, `System.Security`, `System.Security.Cryptography.X509Certificates`.
- **`Views/ErrorView.xaml.cs:2–13`** — Boilerplate generated-but-unused namespaces; not severe but bloats compile-time analysis.
- **`Views/UnregisterView.xaml.cs:2–13`** — Same.
- **`Views/RegisterLicenseView.xaml.cs:2–13`** — Same.
- **`AppResources.xaml` not merged anywhere in this assembly** — only `samples/WpfSampleApp/App.xaml:9` merges it. Inside this library every view re-declares the styles locally. **Fix:** every View's `<Window.Resources>` should reference the shared dictionary via `<ResourceDictionary.MergedDictionaries>` or `BasedOn={StaticResource ...}`.
- **`Converters/ValueConverters/BooleanToVisibilityConverter.cs:11`** — `[ValueConversion(typeof(string), typeof(Visibility))]` — the source type attribute says `string` but the converter handles `bool`. Wrong metadata.
- **`Converters/ValueConverters/BooleanToVisibilityConverter.cs:23`** — Falls through to `Visibility.Visible` for *any non-bool input* (including null). Silent contract violation.
- **`Converters/ValueConverters/BooleanToVisibilityConverter.cs` (ProductNameToIdConverter)** — Caches `NameValueCollection products` as instance state. Converters are typically declared as resources and re-used; if config is reloaded, the converter never sees the change. Low-priority but worth a `// design note` comment.
- **`Rules/ReceiptCodeRule.cs:15`** — Magic number `100` for max length. Move to a `const int MaxReceiptCodeLength = 100;`.
- **`Rules/ReceiptCodeRule.cs:13, 17`** — User-facing messages are hard-coded in English. The project ships `Properties/Resources.resx` (presumably for localization) — this rule should use it.
- **`LicenseManagement.EndUser.Wpf.csproj:11`** — `TargetFrameworkVersion>v4.8.1<` — .NET Framework is in maintenance-only mode. Long-term, recommend multi-targeting `net48` + `net8.0-windows`.

#### Low / Info
- **Naming inconsistency** — fields use mixed conventions: `expires`, `status`, `_fullFileName`, `_mac` (`LicenseViewModel.cs:24–38`). The skill rule is `_camelCase`. Normalize.
- **`LicenseViewModel.cs:11`** — `using LicenseManagement.EndUser.Wpf.Commands;` — `Commands.RelayCommand` is `internal`, but `LicenseViewModel` is public and exposes `ICommand` properties whose backing implementation is internal. That's fine across assemblies (consumers see only `ICommand`), but `RelayCommand` is then unusable by library consumers who want to write their own commands. Either make it `public` or keep but document.
- **`LicenseControl.xaml:10` and `MainWindow.xaml:10`** — `DataContext='{Binding RelativeSource={RelativeSource Mode=Self}, Path=License}'` on the root element. This causes WPF to attempt the binding before the dependency property is initialized; combined with `Meta` returning `null` when there are no app settings, the binding logs a warning every startup.
- **`samples/WpfSampleApp/MainWindow.xaml.cs:77`** — Typo `LicenseStatusTitles.InValidTrial` — looking at `LicenseStatusConverter.cs:32` the canonical name is `InvalidTrial`. Either the consumer SDK has both spellings or this won't compile against the current SDK version.
- **`samples/WpfSampleApp/MainWindow.xaml.cs:108`** — Same `InValidTrial` issue inside the switch expression.

### 2.2 Design-Patterns Audit

#### High value
1. **Strategy/Command for License Operations** — `LicenseViewModel.CheckLiceneFile`, `RenewLicenseFileAction`, `RegisterAction`, `UnregisterLicense` all follow the same shape: build `PublisherPreferences` → build `LicHandlingContext` → instantiate a specific `LicenseHandling*` handler → try/catch/`ShowErrorView`. Extract a single `LicenseOperationRunner` with `Execute(IHandlerFactory, Action<Exception>)` and delete ~80 lines of duplication.
2. **Factory for `PublisherPreferences`** — The exact same 5-property `PublisherPreferences(VendorId, ProductId, ApiKey){ PublicKey, ValidDays }` initializer is written four times (`LicenseViewModel.cs:273, 293`, `RegisterLicenseViewModel.cs:52`, `UnregisterViewModel.cs:23`). Factory method `PublisherPreferences ToPreferences(this LicenseViewModel)`.
3. **Mediator/Dialog service** — Direct construction of dialog windows from view models (`LicenseViewModel.cs:336, 359`, `BaseViewModel.cs:50`) breaks testability. Introduce `IDialogService { void ShowError(Exception); bool ShowRegister(...); bool ShowUnregister(...); }`.

#### Medium value
4. **Adapter for `LicHandlingContext` → `LicenseViewModel`** — `LicenseViewModel.FromContext` and `UpdateFromLicenseModel` carry near-duplicate property-mapping logic (`LicenseViewModel.cs:40–72, 312–331`). Extract a `LicenseContextAdapter`.
5. **Visitor/dictionary over switch chains** — Seven separate `IValueConverter` classes all switch on `LicenseStatusTitles` (`LicenseStatusConverter.cs:24, 55, 86, 117, 148, 169, 191, 212`). A single `Dictionary<LicenseStatusTitles, LicenseStatusPresentation>` keyed by enum, plus a single converter parameterized by the property name, would replace all seven. This is the single largest opportunity for code reduction.
6. **Configuration object pattern** — `MainWindow.Meta` and `LicenseControl.Meta` duplicate ~30 lines of config-reading code (`MainWindow.xaml.cs:49–83` vs `LicenseControl.xaml.cs:55–90`). Extract `LicenseConfigurationLoader`.

#### Don't pattern (anti-recommendation)
- Do **not** introduce DI/IoC just to wire up 4 view models. Project size doesn't justify it.

### 2.3 Security & WPF Memory-Leak Audit

#### Critical
- **`Views/LicenseControl.xaml.cs:70` and `Views/MainWindow.xaml.cs:66`** — `ConfigurationManager.AppSettings.Get("ApiKey")` is stored in a `public LicenseViewModel.ApiKey { get; set; }` property (with `[XmlIgnore]` — `LicenseViewModel.cs:246`). The view model is the DataContext of a window. **Any binding inspector tool (Snoop, Live Visual Tree) instantly reveals the API key in plaintext**. While this is a client-side SDK key (not master), best practice is to never hold it in a publicly-bindable property. **Fix:** keep `ApiKey` in a non-public field or wrap it in a `SecureString`, and inject it into the SDK handler at use-time rather than store it on the bindable view model.

#### High
- **`ViewModels/LicenseViewModel.cs:349, 371`** — `view.Closed += (s, e) => { CheckLiceneFile(thisView); };` — the closure captures `thisView` (the parent `MainWindow`). If the parent window is ever long-lived and `Register`/`Unregister` is opened repeatedly, each closure keeps a reference; on rapid open/close cycles the GC pressure is real. **Fix:** named handler that unsubscribes itself: `EventHandler h = null; h = (s, e) => { view.Closed -= h; CheckLiceneFile(thisView); }; view.Closed += h;`.
- **`Views/MainWindow.xaml.cs:104` and `Views/LicenseControl.xaml.cs:110`** — `Loaded` handler subscribes to the event but there's no corresponding `Unloaded` unsubscribe. For a `UserControl` that's repeatedly added/removed (e.g. tab navigation), this leaks. **Fix:** `Loaded += ...; Unloaded += (s, e) => Loaded -= ...;` or use one-shot pattern.
- **`Views/MainWindow.xaml.cs:124` / `Views/LicenseControl.xaml.cs:120`** — `new BitmapImage(new Uri(...))` is created without `BitmapCreateOptions.IgnoreImageCache` or being frozen. For an icon that lives for the app lifetime this is fine, but the file handle behaviour mentioned in the clean-code skill applies — passing through `BitmapImage` with `CacheOption = BitmapCacheOption.OnLoad` is safer.
- **`Views/LicenseControl.xaml.cs:114` / `Views/MainWindow.xaml.cs:118`** — `Application.ResourceAssembly = Assembly.GetExecutingAssembly();` is **assigned by a library**. This is a process-wide mutable static that the *host application* should own. A library that does this can break a host that has already set `ResourceAssembly` to a different value. **Fix:** remove this line and document that consumers must reference the library's pack URI directly (they already do; this assignment is unnecessary).
- **`samples/WpfSampleApp/Services/LicenseService.cs:32–46`** — Constants `VendorId`, `ProductId`, `ApiKey`, `PublicKey` are placeholder strings, fine for a sample. But the **sample's pattern is `private const string ApiKey = "PUB_...";`** which teaches consumers to commit API keys to source. The class XML docs even say "In a production application, you would typically store credentials in app settings or secure storage" — good, but the code itself contradicts the guidance. **Fix:** load from `ConfigurationManager` in the sample (matches what the library itself does), and add a `README` callout.

#### Medium
- **`ViewModels/LicenseViewModel.cs:265–267`** — Recreating commands on every binding evaluation also breaks `CanExecuteChanged` wiring — the GC'd previous instance may have been subscribed to `CommandManager.RequerySuggested` (had `RelayCommand` actually wired it). Combined with the `RelayCommand` bug above, this is a double leak avenue.
- **`Views/ErrorView.xaml:118–135`** — Three `TextBlock`s bind to `Message`, `InnerException.Message`, `InnerException.InnerException.Message`. If the exception is null or doesn't have nested inners, WPF logs binding errors. Minor, but consider a `ExceptionMessageFormatter`.
- **`Converters/ValueConverters/BooleanToVisibilityConverter.cs:38`** — `private NameValueCollection products;` cached on a converter that may outlive the config it was loaded from. If the host calls `ConfigurationManager.RefreshSection("Products")`, the converter is stale.
- **No CSP / no signature verification considerations apply** (not a web project).

#### Low
- **Strong-name signing** — `Enduser.wpf.snk` is committed to the repo (`LicenseManagement.EndUser.Wpf.csproj:41`). For a public NuGet package this is intentional, but it does mean **anyone can build a binary-compatible build of this assembly with the same strong name**, defeating the typical "tamper-proof" assumption of strong naming. Note: this is the standard limitation of public SNKs; not necessarily a defect, but worth understanding.

### 2.4 External-Integrations Review

The library itself does **not** make direct HTTP calls; all external SDK interaction is delegated to `LicenseManagement.EndUser` (the dependency NuGet). However the orchestration patterns it uses warrant review:

#### High
- **`ViewModels/LicenseViewModel.cs:280–289`** — Generic `catch (Exception)` around `handler.HandleLicense()`. The underlying SDK presumably has documented exception types (e.g. license-not-found, server-unreachable, invalid-signature). All branches go to the same dialog. A user with a temporarily-unreachable server sees the same message as a user with a permanently-invalid receipt. **Fix:** catch specific exception types from `LicenseManagement.EndUser.Exceptions` (which is `using`d at `LicenseViewModel.cs:1` but never referenced — implying the exception types exist and aren't being used).
- **`ViewModels/RegisterLicenseViewModel.cs:68–75`** — Same broad `catch (Exception e)`.
- **`ViewModels/UnregisterViewModel.cs:32–39`** — Same broad `catch (Exception e)`.
- **No retry policy / no timeout configuration is observable at this layer.** This is acceptable *if* the underlying SDK exposes its own timeout/retry, but the library should at minimum document the assumption.
- **No observability** — none of the catch blocks log anything; the exception silently goes to a modal dialog. A production deployment cannot diagnose intermittent server errors. **Fix:** at least `Trace.WriteLine` or `EventSource` write before showing the dialog.

#### Medium
- **`samples/WpfSampleApp/Services/LicenseService.cs:179`** — `_cachedContext?.LicenseModel?.Status == ... .Valid` — uses cached state without a TTL. If the customer cancels their subscription mid-session, `HasProAccess()` keeps returning `true` until next `ValidateLicense()`. Acceptable for a sample, document for production.
- **No idempotency key handling visible** — but again, this is delegated to the SDK. The view models for `Register`/`Unregister` could be invoked twice in quick succession (double-click on "Submit") — `RelayCommand.CanExecute` doesn't disable while a request is in flight. **Fix:** add an `IsBusy` flag in the view model and have `CanExecute` return `!IsBusy && ApiKey != null`.

#### Low
- The SDK trust boundary appears clean — no API endpoints are hand-coded into this assembly.

### 2.5 XAML / WPF-specific Audit

#### High
- **`Views/MainWindow.xaml:193`** — `SelectionChanged='OnProductsSlectionChanged'` (typo "Slection") wired to the misspelled handler `MainWindow.xaml.cs:94`. Compiles, but is a code-smell time-bomb for renames.
- **Resource duplication across 5 XAML files** — 60+ lines of identical `<Thickness>` and `<Style>` declarations exist in `AppResources.xaml`, `MainWindow.xaml`, `LicenseControl.xaml`, `ErrorView.xaml`, `RegisterLicenseView.xaml`, `UnregisterView.xaml`. **Fix:** every view should `<ResourceDictionary.MergedDictionaries><ResourceDictionary Source="pack://application:,,,/LicenseManagement.EndUser.Wpf;component/AppResources.xaml"/></ResourceDictionary.MergedDictionaries>` and delete the local copies. Saves ~250 lines of XAML.
- **Implicit (TargetType-only) styles in `AppResources.xaml`** — `<Style TargetType='StackPanel'>` and `<Style TargetType='Button'>` (`AppResources.xaml:60, 84`) are **applied to every `StackPanel`/`Button` in any consumer app that merges this dictionary**. This is poison for a NuGet library — consumers will see their entire app's button styling mutated. **Fix:** name every implicit style with an `x:Key` so only opt-in elements pick it up.
- **`LicenseControl.xaml:14`** — Declares an instance of `LicenseViewModel` as a resource (`<viewModels:LicenseViewModel x:Key='License' />`) AND binds the control's `DataContext` to its dependency property. If both succeed, the resource instance is created and immediately discarded — but the constructor side effects (none currently) would run. Remove the resource declaration.
- **`Views/MainWindow.xaml:18`** — Same `<viewModles:LicenseViewModel x:Key='License' />` (also note the namespace alias typo `viewModles`).
- **`Window1.xaml` references `<Image Source='{StaticResource license}' />`** but the file has no resource dictionary merged and no resource named `license` — this XAML doesn't render at runtime. Confirms it's dead scaffolding.

#### Medium
- **`Views/RegisterLicenseView.xaml:118`** — `TextBox x:Name='receiptCode'` is reached via code-behind in the view model (`RegisterLicenseViewModel.cs:50`) — name-based coupling. Bind two-way and remove the named access.
- **`AppResources.xaml:48–58`** — Styles `boldText`, `ErrorText`, `grayText` use the cross-cutting `TextElement.FontWeight` attached property without `TargetType`. Works but is brittle; prefer `Style TargetType="TextBlock"` etc.
- **`Views/ErrorView.xaml:135`** — `TextWrapping='WrapWithOverflow'` is unusual (most use `Wrap`); verify intent.
- **`Views/ErrorView.xaml:117`** — `Image Source='/Assets/error.png'` uses an application-relative URI. Since this assembly is a library, the consumer must have the asset in *their* output path or use a pack URI. The asset is declared as `<Resource>` in csproj (line 139), but the path here should be a pack URI for reliability: `pack://application:,,,/LicenseManagement.EndUser.Wpf;component/Assets/error.png`.
- **`samples/WpfSampleApp/MainWindow.xaml`** never displays the actual `LicenseControl` — it builds its own status panel. The sample misses the chance to demonstrate the embeddable control documented in the README.

#### Low
- **`Views/MainWindow.xaml:194`** — `x:Name='productsComboBox'` — naming an element accessed from code-behind is fine, but again the binding `SelectedItem='{Binding Product}'` already provides programmatic access via the VM.
- **Many XAML attribute values use single quotes** (`'Bold'` vs `"Bold"`) — valid XML but unusual; style is consistent within the project, so leave alone.

### 2.6 Project / Build / Packaging Audit

#### High
- **`LicenseManagement.EndUser.Wpf.csproj:159`** — `<HintPath>packages\LicenseManagement.EndUser.2.0.0\lib\net481\LicenseManagement.EndUser.dll</HintPath>` is hard-coded to version 2.0.0. Bumping the SDK version requires editing two places (here and `packages.config`). Consider a property: `<LicenseEndUserVersion>2.0.0</LicenseEndUserVersion>`.
- **`nugetSpec.nuspec:23`** — Bundles `LicenseManagement.EndUser.dll` directly **without a `<dependency>` declaration**. This means the consumer's NuGet graph has no visibility into the transitive SDK version. If the consumer also installs `LicenseManagement.EndUser` directly at a different version, you have a runtime assembly-loading conflict. **Fix:** prefer `<dependencies>` over `<files>` for shared NuGet packages, unless this is a deliberate "fat package" decision (CHANGELOG 1.3.3 implies it is — then document that consumers must not install the SDK separately).
- **`.github/workflows/publish.yml:54, 65`** — Pins `LicenseManagement.EndUser` to `2.0.0` and `Hymma.HttpClientFactory` to `1.0.8` as hard-coded strings. When the SDK bumps to 2.1.0 the WPF publish workflow will silently keep building against 2.0.0. **Fix:** read from `packages.config` or pass as workflow input.
- **`.github/workflows/build.yml`** — No `dotnet test` step (because there are no tests). At minimum, the build job should fail if warnings are emitted (`/p:TreatWarningsAsErrors=true`).

#### Medium
- **`LicenseManagement.EndUser.Wpf.csproj`** — Uses the **old-style csproj** (`<Project ToolsVersion="15.0">`) which requires every file to be listed individually. The new SDK-style csproj (`<Project Sdk="Microsoft.NET.Sdk">`) would auto-discover compile items and shrink this file to ~20 lines. Worth the migration even on `net481`.
- **`LicenseManagement.EndUser.Wpf.csproj:38`** — `<SignAssembly>true</SignAssembly>` is set without a key-file path on the same line (it's at line 41 in a separate `<PropertyGroup>`). Functionally equivalent but disorganized.
- **`Properties/AssemblyInfo.cs:54–55`** — Hard-coded `2.0.0.0` while `CHANGELOG.md` reports `2.0.1`. Assembly version is out of sync with the package version. The publish workflow updates the *nuspec* version but not the *AssemblyInfo* version → consumer `Assembly.GetName().Version` returns `2.0.0.0` even on package `2.0.1`.
- **`samples/WpfSampleApp/WpfSampleApp.csproj:51`** — `Version="2.*"` floating reference to the package. This is convenient for the sample but if `3.x` ships, the sample silently breaks. Pin to `2.*` deliberately if cross-version compatibility is intended; else use `[2.0.0,3.0.0)`.
- **`packages.config:3-15`** — Indirect dependencies (`System.Buffers`, `System.Memory`, etc.) are listed individually. SDK-style csproj would resolve these transitively.
- **`packages.config`** — Mixes runtime dependencies (`Hymma.HttpClientFactory`, `Hymma.Lm.EndUser`) — the latter package name `Hymma.Lm.EndUser` looks like the *legacy* name. Combined with `csproj` referencing `LicenseManagement.EndUser` (the new name), the package graph is inconsistent. **Verify** that `packages.config:7` (`Hymma.Lm.EndUser 1.2.0`) shouldn't be `LicenseManagement.EndUser 2.0.0`.

#### Low
- **`Enduser.wpf.snk` is committed.** As noted, intentional for public NuGet; ensure README mentions assembly is strong-named.
- **`padlock.ico` exists at the repo root AND `Assets/padlock.ico`** (two copies). The `.csproj:147` references only the root one. Pick one.
- **`Properties/AssemblyInfo.cs:15`** — Copyright says "2025" but `CHANGELOG.md` shows entries from 2024 and 2026. Update yearly.
